在我們前幾次讓 AI 開發的嘗試中，我們都用了相同的工具
(/grill-me, /prototype, /to-tickets)...

但前幾次都迎來了災難性的失敗。

早期嘗試的血淚教訓

  • 資源失控：開發超過 2 小時，消耗海量 Token。
  • Bug 叢生：牽一髮動全身，改了後端壞了前端。

雷區一：無止盡的過度設計 (Over-engineering)

AI 很容易把架構想得太複雜。在早期的討論中，AI 偷偷引入了 Keycloak BFF、分散式交易、對帳佇列等企業級架構，導致實作超出負荷。

雷區二：「垂直切片 (Vertical Slices)」的死穴

預設的 /to-tickets 會切出包含「DB + API + UI」的垂直功能票。

單一 AI 執行
Context Window 被各種前後端檔案塞爆，AI 記憶體超載開始胡言亂語。
多 AI 平行執行
所有 AI 都在搶著改 App.tsx 和 Controller，爆發無解的 Merge Conflicts。

最終版破局關鍵一：殘酷的減法

在 Grill 與 Prototype 階段，人類必須扮演拉住韁繩的「架構師」。
確保 MVP 極簡，讓 AI 保持思緒清晰。

我們果斷決定的「不」做：
❌ 不做真實 Auth → Mock UserContext
❌ 不做複雜狀態管理 → 純 fetch API
❌ 不做 Server 端分頁 → Client-side 處理
👉 Demo 時間：展示用過即丟的 Prototype 👈

最終版破局關鍵二：物理隔離切票

人類的刻意介入：強迫打破 /to-tickets 的垂直切片慣例。
下達指令：「必須將票嚴格分成 frontend 與 backend 兩群，避免改到同一檔案。」 


┌──────────┐     ┌──────────┐
│ Ticket01 │────▶│ Ticket02 │──┐ Backend Session (無干擾)
│ BE 骨架  │     │ BE API   │  │
└──────────┘     └──────────┘  │
                               ▼
                         ┌──────────┐
                         │ Ticket05 │ Integration Session
                         │ 整合驗證 │
                         └──────────┘
┌──────────┐     ┌──────────┐  ▲
│ Ticket03 │────▶│ Ticket04 │──┘ Frontend Session (無干擾)
│ FE 骨架  │     │ FE 互動  │

極速交付：從 2 小時到 20 分鐘

  • Backend Session 專心處理後端，Frontend Session 平行處理前端。
  • 效益：零檔案衝突、Context 大幅瘦身、Token 成本銳減。
  • 最後靠 Integration Session 完美接合。

如何避免 AI 再次暴走？
建立專案「開發鐵律」

將團隊的做事標準寫入專案根目錄的 CLAUDE.md 或 CONTEXT.md，
讓 AI 每次啟動都受到邊界約束，根絕過度設計。

# 開發鐵律範例

1. 永遠先做 MVP： 所有新功能必須先規劃 Phase 1 (核心業務) 與 Phase 2 (外圍整合)。

2. 禁止過度設計： 除非人類明確要求，否則不准自行引入微服務架構或複雜的 Message Queue。

3. 套用公司標準： 嚴禁自行發明 Auth 邏輯！實作認證時，必須直接套用 reference-code/KeycloakFilter.java 範本。

效益：連最難的企業級 OIDC 認證，都從「發明架構(1小時)」降維成「複製貼上(1分鐘)」。

總結：人類工程師的新價值

  1. 掌控架構邊界：AI 很容易把事情複雜化，我們必須守住 MVP 的底線。
  2. 改變切票思維：讓多個 Agent 平行協作的前提，是創造「實體目錄隔離」的工作指派。
  3. 角色轉換：我們不再是敲鍵盤寫 Code 的機器，而是引導 AI 協作的「系統分析師 (SA)」與「專案經理 (PM)」。
